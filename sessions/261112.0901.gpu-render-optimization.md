# Optimisation du rendu et qualification sans fenêtres

Action line: [terminal.gpu](../landscapes/261111.2216.terminal-gpu.md)

Target: [Candidat isolé](../landscapes/261111.2216.terminal-gpu.md#candidat-isole)

## Result

Candidat zterm2 0.1.2 Development arm64, identité org.henarkon.zterm2, construit, mesuré et conservé localement. GPU Kitty toujours opt-in avec ZTERM2_KITTY_GPU=1. Aucune installation, aucun remplacement d’iTerm2 ; correctifs non committés et non publiés, session CPS propriétaire active. Aucune MR/PR ni envoi de rapport au serveur iTerm2 ; aucun arbre source Cardo/Vigil modifié.

Conversion sRGB par table ICC 64³ et passe de rendu Metal préparée avant l’encodeur principal, dans le même command buffer. Suppression de l’attente CPU par image ; repli Core Image conservé pour les entrées non qualifiées. Pixels Kitty originaux conservés dans iTermImage pour éviter le détour AppKit. Pool : 4 emplacements / 64 Mio incluant textures et buffers d’envoi ; LUT comptée séparément, allocation observée 2113536 octets. Génération par plans avec moins de 1 Mio de travail temporaire CPU. Ressources retenues jusqu’à fin GPU, y compris si le cache est drainé avant soumission.

La limite CI, le chargement transitoire et la suppression seule de la file dédiée n’expliquaient ni ne supprimaient le surcoût. La contre-épreuve décisive remplace le calcul Metal par une passe de rendu existante : environ 50–60 Mio supprimés dans l’application. Attribution au parcours de calcul et à ses allocations pilote hors pool ; les sites internes précis du pilote ne sont pas directement prouvés.

## Qualification

26 tests Python, 33 tests natifs ciblés (dont la régression de sélection des rapports), 36 cas couleur/alpha et 589824 couleurs denses passent ; erreur maximale 1/255. Réutilisation, budgets réels, tailles, drain et rétention vérifiés ; un consommateur GPU dans le même lot voit les bons pixels sans attente CPU.

Cohorte visible propre, recueillie avant la demande utilisateur d’arrêter les fenêtres : ancien GPU CPU moyen 38,54 % d’un cœur et pics d’empreinte moyens 308,14 Mio ; nouveau GPU 35,27 % et 255,95 Mio. Réductions relatives 8,5 % CPU et 16,9 % mémoire, seulement deux répétitions par parcours. Cohorte de contre-épreuve calcul vs rendu conservée distinctement sous measurements/compute.

Cohorte finale sans fenêtres : même binaire exactement identifié par SHA, pixels synthétiques 640×360 opaques, 80×25 cellules, 30 images/s, stabilisation 7 s et préchauffage 1 s ; environ 3 s mesurées. CPU 38,43–38,91 % d’un cœur pour conversion CPU contre 35,51–35,86 % pour GPU, soit -7,7 % relatif. Empreinte 205,86–206,28 / 215,83–216,49 Mio : reste un petit surcoût face au CPU, distinct de l’ancien surcoût GPU. Ne pas mélanger les valeurs absolues de cette cohorte avec les essais visibles.

Mode de test conditionné à l’identité du fork et à deux variables explicites : commandes de mise au premier plan et activation bloquées, profil Display P3 fixe. Le banc refuse les anciens exécutables sans cette capacité et exige au moins 60 lots GPU mesurés, plus au moins 90 conversions. Ici : 90 lots / fenêtre mesurée et 120 images acquittées, une seule image partagée en attente, zéro objet restant. Viewport 587×429, échelle 1, ICC SHA256 0ff6958f98684c61f6bbdce1368ddeaf3873baf84545baba482e920d92a914c0. Toutes ces conditions doivent correspondre entre parcours. Les lancements normaux gardent le profil écran et leur comportement habituel.

Quatre relevés GPU dédiés sans fenêtres : nouveau GPU 0,105–0,251 ms par lot en moyenne ; il s’agit d’enveloppes de commandes de l’application et non d’occupation matérielle exclusive. Compteur pilote global 0–32 % selon les relevés, incluant autres applications et WindowServer ; aucune attribution exclusive. powermetrics exigeait un mot de passe, aucune saisie ; lecture des compteurs IORegistry et horodatages Metal utilisée à la place.

Tous les essais applicatifs : garde 512 Mio/processus et 20 s, échantillonnage nominal 50 ms. Le GPU n’est pas activé par défaut et aucune cadence de présentation physique n’est revendiquée.

## Limits and incidents

L’utilisateur a signalé la fenêtre du rapporteur. Cause démontrée : le préfixe zterm2- acceptait les anciens rapports zterm2-texture-harness de la veille. Aucun rapport récent de crash de l’application trouvé dans les dossiers utilisateur inspectés. Filtrage par timestamp corrigé, envoi amont neutralisé pour le fork, test de régression réussi. Les anciennes mesures v0.1.1 restent immuables avec un erratum v0.1.2 ; elles ne constituent plus une qualification propre. Les essais visibles ont été arrêtés à la demande ; tous les nouveaux essais sont sans fenêtres.

Les anciens essais avaient laissé des serveurs de restauration détachés. Vingt-huit serveurs correspondant exactement aux suites présentes dans nos observations ont été arrêtés ; les processus non attribués ont été préservés. Les nouveaux essais désactivent cette restauration uniquement dans leurs arguments de lancement jetables.

Une première paire invisible a été rejetée pour divergence du profil couleur ; le profil et le viewport sont désormais contrôlés, aucune moyenne entre conditions différentes. LUT grossière universelle rejetée pour erreur de gamut ; seul le chemin sRGB qualifié utilise la table compacte, les autres entrées gardent CI. Les tentatives rejetées ne sont pas présentées comme optimisations validées.

Scène Kitty synthétique uniquement : ni GIF animé, ni décodage vidéo, ni Cardo/Battle of Yavin ou application de production. Le renderer GIF historique contient encore redimensionnement, retournement et préparation de textures par trame ; son cache annonce l’éviction de trames inactives à vérifier par profilage avant modification.

## Recommended next action

Profiler un petit GIF animé réel en mode invisible et sous les mêmes gardes : décodage, composition/redimensionnement, retournement, conversion, transfert et taux de défaut/éviction du cache. Mesurer avant d’étendre le recyclage ou le chemin GPU à ce renderer. Garder le GPU off par défaut, élargir ensuite les contrôles visuels et de latence avec une qualification séparée autorisée ; aucune fenêtre visible sans demande explicite de l’utilisateur.
